Lesson 01 · 10 minutes

先把 review 看成兩層 loop

你對 harness 的直覺是對的：這裡確實有 prompt、LLM、tools、state。但理解它的關鍵是先分開「逐檔派工」和「單檔對話」兩個 loop。

核心心智模型 diff review retrieval practice
本課完成標準： 你能指出一次 review 中，哪個函式決定 review 哪些檔案，哪個函式真正反覆呼叫 LLM，以及 finding 何時進入 collector。

1. 先看全貌

diff review 的主路徑可以先壓成這條線：

  1. executeReviewContextWithStage組裝 template、rules、LLM runtime、built-in tools、MCP tools。
  2. agent.New建立 session、manifest，並注入一個共用的 llmloop.Runner。
  3. agent.Run解析 diff、建立 DiffMap、過濾檔案、估算 token budget。
  4. dispatchSubtasks每個 changed file 啟一個受 concurrency 與 timeout 控制的 subtask。
  5. executeSubtask渲染 plan/main prompt，然後把單檔 conversation 交給 Runner。
  6. RunPerFileLLM → tool calls → tool results → 下一輪，直到 task_done 或 stop。

Source：review_cmd.go、agent.go、loop.go。

2. Harness 元件要放在哪一層

Prompt

task_template.json 指向 prompt 檔案；executeSubtask 再把 {{diff}}、{{current_file_path}}、{{system_rule}} 等 placeholder 替換成這一檔的實際資料。

所以 template 是靜態藍圖，真正送出的 messages 是 per-file、per-run 的結果。

Tool schema

tools.json 經過 BuildToolDefs 變成 llm.ToolDef。它只描述模型可見的名稱、說明和參數，不會自己執行。

Tool implementation

buildToolRegistry 將 file_read、file_find、file_read_diff、code_search、code_comment 綁到 Go Provider。MCP tools 也註冊進同一個 registry。

LLM loop

RunPerFile 將 MainToolDefs 放進每次 ChatRequest，讀取 response 的 tool calls，再由 executeToolCall 執行。

3. 一輪 tool call 實際發生什麼

messages
  ↓
LLMClient.CompletionsWithCtx(messages, MainToolDefs)
  ↓
assistant response: code_search(...)
  ↓
executeToolCall → Registry.Get → Provider.Execute
  ↓
tool result
  ↓
messages += assistant tool call + tool result
  ↓
下一次 CompletionsWithCtx

模型的回覆如果沒有 tool call，loop 會補一個 retry 訊息。模型呼叫 code_comment 時，runtime 會解析 comment、用目前檔案路徑覆寫模型可能 hallucinate 的 path，必要時重新定位行號，最後加入 CommentCollector。模型呼叫 task_done 且 state 是 DONE，這個檔案才算完成。

這裡最容易搞混的三件事

  1. ToolDef 不是 tool。 前者是給 LLM 看的 schema，後者是 registry 裡真正會執行的 Provider。
  2. Agent 不是單一 conversation。 Agent 管整個 diff review；Runner 的一次 RunPerFile 才是單一檔案的 conversation。
  3. code_comment 不是最終輸出。 它先進 collector，之後還要經過 review filter、manifest/session 和 emitter。

顯示自我檢查

第一個角色是 ToolDef：它讓模型知道名稱和參數 schema。第二個角色是 Registry 裡的 Provider：executeToolCall 依名稱找到它並執行，結果再被包成 tool-result message append 回 conversation。

  • RunPerFile / executeToolCall：看真正的 round-trip。
