Правила указывают OCR, **на чём сосредоточиться** при ревью каждого файла. Они хранятся в JSON-файлах на трёх уровнях, а также во встроенном системном наборе по умолчанию, который поставляется вместе с бинарным файлом.

## Цепочка приоритетов

OCR разрешает правила с помощью **цепочки приоритетов из четырёх уровней**. Для каждого пути файла уровни проверяются по порядку; побеждает первый совпавший шаблон.

| Приоритет | Источник | Путь | Примечания |
|---|---|---|---|
| 1 (наивысший) | флаг `--rule` | указанный пользователем | Переопределение CLI; при передаче всегда имеет приоритет. |
| 2 | Конфигурация проекта | `<repoDir>/.opencodereview/rule.json` | Правила проекта — их безопасно коммитить. |
| 3 | Глобальная конфигурация | `~/.opencodereview/rule.json` | Настройки для всех проектов пользователя. |
| 4 (наименьший) | Системное значение по умолчанию | встроенный `system_rules.json` | Встроенные правила для распространённых языков. |

Если файл уровня с более высоким приоритетом не существует, он молча пропускается — это не ошибка. Поэтому проект без `.opencodereview/rule.json` просто переходит к глобальному / системному уровням.

Системный уровень присутствует **всегда** (он включён в бинарный файл), поэтому итоговое правило найдётся всегда.

## Формат файла правил (уровни 1–3)

```json
{
  "include": ["src/**/*.{ts,tsx}", "src/**/*.go"],
  "exclude": ["**/*.test.ts", "**/generated/**"],
  "rules": [
    {
      "path": "src/api/**/*.go",
      "rule": "Все экспортируемые обработчики должны проверять тела запросов перед использованием."
    },
    {
      "path": "**/*mapper*.xml",
      "rule": "Проверяйте SQL на риски инъекций, ошибки параметров и отсутствие закрывающих тегов."
    }
  ]
}
```

Три независимых поля:

- `include` — необязательное. Glob-шаблоны, которые *обходят* встроенные исключения по умолчанию (исключения тестовых файлов — см. ниже). Это не белый список: файлы, не совпавшие ни с одним шаблоном `include`, всё равно проходят проверки `unsupported_ext` и `default_path` и могут быть отправлены на ревью.
- `exclude` — необязательное. Glob-шаблоны файлов, которые OCR *не должен* проверять. Имеет наивысший приоритет внутри фильтра.
- `rules` — массив записей `{path, rule}`, вычисляемых **в порядке объявления**. Первый `path`, glob которого совпадает с файлом, определяет подсказку, которую OCR отправляет модели для этого файла.

### Возможности glob

Для сопоставления OCR использует [`bmatcuk/doublestar/v4`](https://pkg.go.dev/github.com/bmatcuk/doublestar/v4):

- `*` — сопоставляет любые символы, кроме `/`.
- `**` — сопоставляет путь через границы каталогов (`src/**/*.go` охватывает любую глубину).
- `{a,b,c}` — раскрытие фигурных скобок. `*.{ts,tsx,js,jsx}` раскрывается в четыре шаблона и проверяется по очереди.
- `?` — сопоставляет один символ.
- `[abc]` — класс символов.

> Шаблоны сопоставляются **без учёта регистра** (путь файла перед сопоставлением переводится в нижний регистр). Если сомневаетесь, используйте `ocr rules check <path>` для проверки.

## Как фильтруются файлы

Фильтр — это алгоритм из пяти проверок в [`internal/agent/preview.go`](https://github.com/alibaba/open-code-review/blob/main/internal/agent/preview.go). Для каждого diff OCR задаёт вопросы:

1. **`binary`** — файл бинарный? Исключить.
2. **`user_exclude`** — путь совпадает с каким-либо пользовательским шаблоном `exclude`? Исключить.
3. **`user_include`** — пользователь задал `include`, и путь совпадает? Если да, **сохранить сразу** (обходит проверки `unsupported_ext` и `default_path` ниже).
4. **`unsupported_ext`** — расширение файла находится в [разрешённом списке](https://github.com/alibaba/open-code-review/blob/main/internal/config/allowlist/supported_file_types.json)? Если нет, исключить.
5. **`default_path`** — путь совпадает со встроенным шаблоном исключения тестовых файлов (`**/*_test.go`, `**/*.test.{js,jsx,ts,tsx}`, `**/*_spec.rb`, …)? Исключить.

Файлы, прошедшие все пять проверок, отправляются в LLM. Причина `deleted` (не проверка — она вычисляется отдельно в `Preview()`) отмечает файлы, чей новый путь равен `/dev/null`; нового содержимого для ревью нет. Используйте `ocr review --preview`, чтобы вывести результат фильтра без расхода токенов.

### Исключения путей по умолчанию

Встроенный список исключений (см. [`internal/config/allowlist/default_exclude_patterns.json`](https://github.com/alibaba/open-code-review/blob/main/internal/config/allowlist/default_exclude_patterns.json)) соответствует шаблонам тестовых файлов:

- `**/*_test.go`
- `**/src/test/java/**/*.java`
- `**/src/test/**/*.kt`
- `**/*.test.{js,jsx,ts,tsx}`
- `**/*.spec.{js,jsx,ts,tsx}`
- `**/__tests__/**`
- `**/test/**/*_test.py`
- `**/tests/**/*_test.py`
- `**/*_test.py`
- `**/*_spec.rb`
- `**/spec/**/*_spec.rb`
- `**/*Test.java`
- `**/*Tests.java`
- `**/*_test.rs`
- `**/oh_modules/**`
- `**/*.test.ets`

Фильтрация шумных каталогов (`vendor/`, `node_modules/`, `target/`, …) происходит раньше, на уровне diff в [`internal/diff/git.go`](https://github.com/alibaba/open-code-review/blob/main/internal/diff/git.go), до запуска фильтра по файлам.

Чтобы выполнить **ревью** файла, совпадающего с одним из шаблонов тестовых файлов, добавьте его в пользовательский список `include` — это переопределит проверку `default_path`.

## Разрешение правила для файла

После того как фильтрация решит, что файл *будет* проверен, OCR выбирает текст правила для агента:

1. Проверяет пользовательский уровень `--rule` в порядке объявления.
2. Проверяет `<repo>/.opencodereview/rule.json` в порядке объявления.
3. Проверяет `~/.opencodereview/rule.json` в порядке объявления.
4. Использует встроенный системный уровень правил.

Встроенный `system_rules.json` содержит следующие шаблоны (по порядку):

| Шаблон | Документ правила |
|---|---|
| `**/*.properties` | `properties.md` — файлы i18n / конфигурации. |
| `**/*{mapper,dao}*.xml` | `mapper_dao_xml.md` — SQL мапперов в стиле MyBatis. |
| `**/pom.xml` | `pom_xml.md` — зависимости Maven. |
| `**/build.gradle` | `build_gradle.md` — зависимости Gradle. |
| `**/package.json` | `package_json.md` — зависимости / скрипты NPM. |
| `**/Cargo.toml` | `cargo_toml.md` — манифест Rust. |
| `**/*.{json,json5}` | `json.md` — универсальный JSON (также соответствует `.json5`). |
| `.github/workflows/**/*.{yaml,yml}` | `github_workflows.md` — YAML рабочих процессов GitHub Actions. |
| `.github/**/*.{yaml,yml}` | `github_config.md` — прочий YAML конфигурации `.github`. |
| `**/*.{yaml,yml}` | `yaml.md` |
| `**/*.java` | `java.md` |
| `**/*.{ftl,ftlh,ftlx}` | `freemarker.md` — шаблоны FreeMarker (SSTI / XSS / обработка null). |
| `**/*.ets` | `arkts.md` — ArkTS / HarmonyOS. |
| `**/*.{ts,js,tsx,jsx}` | `ts_js_tsx_jsx.md` |
| `**/*.{kt}` | `kotlin.md` |
| `**/*.rs` | `rust.md` |
| `**/*.{cpp,cc,hpp}` | `cpp.md` |
| `**/*.c` | `c.md` |
| *(резервный вариант)* | `default.md` |

Итоговое тело правила подставляется в заполнитель `{{system_rule}}` в подсказках плана и основной задачи.

## Проверка выбранного правила: `ocr rules check`

```bash
$ ocr rules check src/main/java/com/example/UserService.java
Файл: src/main/java/com/example/UserService.java
Источник: встроенное системное
Шаблон: **/*.java
Правило:
────────────────────────────────────────
…содержимое java.md…
────────────────────────────────────────
```

```bash
$ ocr rules check --rule custom.json src/main/resources/mapper/UserMapper.xml
Файл: src/main/resources/mapper/UserMapper.xml
Источник: пользовательское (--rule)
Шаблон: **/*mapper*.xml
Правило:
────────────────────────────────────────
…содержимое вашего пользовательского правила…
────────────────────────────────────────
```

Используйте команду, когда правило ведёт себя не так, как вы ожидали: она покажет победившие **уровень** и **шаблон**.

## Рецепты

### На уровне проекта: обеспечить соблюдение стандарта кода

Сохраните как `<repo>/.opencodereview/rule.json` и закоммитьте:

```json
{
  "rules": [
    {
      "path": "src/api/**/*.go",
      "rule": "Каждый публичный обработчик должен выполнять `defer tx.Rollback()` сразу после начала транзакции."
    },
    {
      "path": "**/*mapper*.xml",
      "rule": "Проверяйте SQL на риски инъекций, отсутствие привязки параметров и незакрытые XML-теги."
    }
  ]
}
```

### На уровне проекта: пропустить сгенерированный код, сосредоточиться на src

```json
{
  "include": ["src/**/*.{ts,tsx,js,jsx}"],
  "exclude": ["**/*.gen.ts", "**/generated/**"]
}
```

При заданном `include` файлы внутри `src/` сохраняются, даже если иначе были бы исключены встроенным шаблоном по умолчанию (например, тестовый файл). Файлы вне `src/` всё ещё проходят обычные проверки расширения / пути по умолчанию: `include` — это обход, а не белый список.

### Переопределение для конкретного PR

```bash
ocr review --rule ./.review-rules-only-for-this-pr.json
```

Обходит уровни проекта и глобальный — удобно, когда одному PR нужен совершенно другой контрольный список ревью (например, только проверка безопасности).

### Глобальные личные настройки

Поместите их в `~/.opencodereview/rule.json`, чтобы каждый репозиторий на вашем компьютере их наследовал:

```json
{
  "rules": [
    {
      "path": "**/*.{ts,tsx,js,jsx}",
      "rule": "Всегда проверяйте необработанные отклонения Promise; предупреждайте об `// eslint-disable` без комментария с причиной."
    }
  ]
}
```
