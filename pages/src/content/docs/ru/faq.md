Распространённые ошибки, неожиданное поведение и вопросы «так и должно быть?». Если вашей проблемы здесь нет, создайте [GitHub issue](https://github.com/alibaba/open-code-review/issues), указав выполненные шаги и полный вывод.

## Конфигурация и запуск

### `no valid LLM endpoint configured`

```
no valid LLM endpoint configured; one of OCR_LLM_URL/OCR_LLM_TOKEN/OCR_LLM_MODEL,
~/.opencodereview/config.json, or ANTHROPIC_BASE_URL/ANTHROPIC_AUTH_TOKEN/
ANTHROPIC_MODEL must be set
```

OCR прошёл всю цепочку разрешения endpoint ([Конфигурация](../configuration/#reuse-existing-environment-variables)) и не нашёл полного набора `(URL, token, model)`. Выполните одно из следующих действий:

- задайте `llm.url`, `llm.auth_token` и `llm.model` через `ocr config set`, чтобы заполнить `~/.opencodereview/config.json`;
- экспортируйте `OCR_LLM_URL`, `OCR_LLM_TOKEN` и `OCR_LLM_MODEL`;
- экспортируйте `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN` и `ANTHROPIC_MODEL`, если уже используете Claude Code.

Затем выполните `ocr llm test`, чтобы проверить подключение перед повторным ревью.

### `ocr llm test` показывает неверный источник

OCR использует **первый** полный набор, а не последний. Поэтому, если в файле конфигурации есть все три ключа `llm.*`, переменные окружения игнорируются. Чтобы переменные окружения получили приоритет, удалите ключи конфигурации (`rm` файл или уберите их вручную) либо используйте `ocr config set` для новых значений.

### 401 / 403 от `ocr llm test`

У токена нет нужной области доступа, он истёк либо предназначен для другого поставщика. Anthropic и OpenAI используют разные заголовки авторизации и форматы URL; проверьте соответствие `llm.use_anthropic` выбранному URL:

- Anthropic: URL заканчивается на `/v1/messages`, `use_anthropic=true`.
- OpenAI / совместимый с OpenAI: URL заканчивается на `/v1/chat/completions`, `use_anthropic=false`.

### `not a git repository`

`ocr review` запускает `git diff` (и `git ls-files` для неотслеживаемых файлов) в текущем каталоге. Вне рабочего дерева Git команда завершается сразу. Перейдите в репозиторий или передайте `--repo /path/to/repo`.

### «No tool calls parsed» (локальные модели / Ollama)

```
[ocr] No tool calls parsed for src/foo.go, retrying...
[ocr] Max tool requests reached for src/foo.go.
```

Если каждое ревью повторяет `No tool calls parsed`, заканчивается `Max tool requests reached` и не создаёт комментариев, проблема в модели, а не в конфигурации. OCR полностью управляет ревью через вызовы инструментов, поэтому **модель должна поддерживать нативный tool calling (function calling)**. Модель, которая лишь *описывает* вызовы инструментов текстом (или внутри блоков `<think>`), не сможет работать с OCR независимо от настройки prompt; обычный пример — `deepseek-r1`. Модели с нативной поддержкой инструментов, например `qwen3`, работают. В Ollama выбирайте модели с меткой tools: <https://ollama.com/search?c=tools>.

Проверьте локальную модель напрямую, без OCR:

```bash
curl http://127.0.0.1:11434/v1/chat/completions -H "Content-Type: application/json" -d '{
  "model": "qwen3:32b",
  "messages": [{"role": "user", "content": "The code below has a bug, use the report_bug tool to report it.\n\nfunc add(a, b int) int {\n  return a - b\n}"}],
  "tools": [{"type": "function", "function": {"name": "report_bug", "description": "Report a bug in the code",
    "parameters": {"type": "object", "properties": {"line": {"type": "integer"}, "description": {"type": "string"}}, "required": ["description"]}}}]
}'
```

Успех: ответ содержит структурированный массив `tool_calls` с `report_bug`. Ошибка: «вызов» находится текстом в `content`. Если модель поддерживает инструменты, но медленно отвечает на локальном оборудовании, увеличьте тайм-аут LLM: см. [Тайм-ауты](../configuration/#timeouts).

## Фильтрация и правила

### Мой файл не попал в ревью

Запустите `ocr review --preview` (без затрат на LLM). Вывод содержит каждый кандидат и **причину**, по которой он оставлен или исключён:

```
src/foo.go              modified
src/foo_test.go         modified  (excluded: user_exclude)
node_modules/lib.js     added     (excluded: default_path)
imgs/logo.png           binary    (excluded: unsupported_ext)
```

Пять причин исключения соответствуют проверкам в [фильтре файлов](../review-rules/#how-files-are-filtered):

| Причина | Решение |
|---|---|
| `binary` | Ничего: у бинарных файлов нет текста для ревью. |
| `user_exclude` | Удалите шаблон из списка `exclude`. |
| `unsupported_ext` | Добавьте расширение в `include`, чтобы обойти allowlist. |
| `default_path` | Добавьте файл в `include`: это переопределит встроенные исключения тестовых файлов. |
| `deleted` | Ничего: нового содержимого для ревью нет. |

### Моё пользовательское правило не срабатывает

Выполните `ocr rules check <file-path>`. Команда выводит совпавшие **слой** и **glob-шаблон**:

```
File: src/api/UserHandler.go
Source: Project (.opencodereview/rule.json)
Pattern: src/api/**/*.go
Rule: …
```

Если слой неверный (например, выводится «System built-in», хотя ожидалось правило проекта), вероятно, важен **порядок объявления**: побеждает первый совпавший шаблон. Переместите более специфичное правило выше в массиве `rules` или исправьте glob.

### Не работает раскрытие фигурных скобок

`bmatcuk/doublestar/v4` поддерживает скобки `{ts,tsx}`. Если совпадений нет, проверьте лишние пробелы: `{ts, tsx}` с пробелом молча не совпадёт с `tsx`.

## Ревью

### Файл получил ноль комментариев: он вообще проверялся?

Откройте [просмотр сессий](../viewer/) (`ocr viewer`), найдите сессию и посмотрите дорожку `main_task` файла:

- есть вызовы инструментов и конец на `task_done` → ревью успешно завершено;
- есть вызовы инструментов, но цикл оборван → найдите карточку ошибки;
- карточек `main_task` нет → файл был отфильтрован до ревью; см. [Фильтрация и правила](#фильтрация-и-правила).

### Комментарии содержат `start_line: 0` и `end_line: 0`

OCR не смог привязать комментарий к точной строке в диффе. Частые причины:

- модель пересказала `existing_code`, а не скопировала его дословно из диффа;
- необычное форматирование диффа (CRLF, смешанные табуляции и пробелы) нарушило поиск скользящим окном.

Комментарий всё равно корректен, просто его расположение не определено автоматически. Большинство интеграций агентов (SKILL, плагин Claude Code) сами читают `existing_code` и находят место в файле.

### Превышен порог токенов

```
[ocr] WARNING: prompt tokens (94000) exceed 80% of max_tokens(58888) for src/big.sql
```

Первоначальный prompt файла (правило + дифф + список изменённых файлов) уже превышал 80 % от `MAX_TOKENS = 58888`, ещё до ответа модели. OCR пропускает файл и продолжает работу; в JSON-режиме это также появится в `warnings`.

Что можно сделать:

- добавьте автоматически сгенерированный файл в `exclude`;
- разбейте большой рефакторинг на меньшие коммиты;
- для серии небольших коммитов используйте режим `--commit`, а не проверяйте всё разом в workspace mode.

### Фаза планирования идёт очень долго, хотя файл мал

Сначала выполните `ocr review --preview`. Если `lines.changed` файла больше `PLAN_MODE_LINE_THRESHOLD` (по умолчанию **50**), запускается фаза планирования. Это ожидаемо: большим диффам полезен проход планирования. Для одного ревью используйте меньший дифф или временно измените встроенный шаблон (расширенный вариант; потребуется переопределить `--tools`).

### «Max tool requests reached»

```
[ocr] Max tool requests reached for src/foo.go.
```

Модель выполнила 30 (`MAX_TOOL_REQUEST_TIMES`) раундов использования инструментов, не вызвав `task_done`. Комментарии, созданные до этого, всё равно собираются и выводятся. Если это происходит с большинством файлов, обычно причина одна из следующих:

- модель плохо соблюдает указание «вызывать `task_done` по завершении»; выберите более сильную модель, например Claude Opus;
- инструмент постоянно возвращает ошибку, и модель повторяет вызов; изучите JSONL сессии: повторяющийся результат инструмента покажет причину;
- файл действительно большой или требует много контекста; измените лимит `--max-tools <n>` (например, `--max-tools 40` или `--max-tools 15`). Значения 1–9 ограничиваются снизу до 10; `0` (по умолчанию) использует значение шаблона 30;
- модель не поддерживает нативный tool calling; см. [«No tool calls parsed»](#no-tool-calls-parsed-локальные-модели--ollama).

### Некоторые подагенты падают, но запуск завершается с кодом 0

Так задумано. OCR изолирует ошибки отдельных файлов, чтобы один проблемный файл не прерывал ревью из 20 файлов. Общий код завершения — `0`, если успешен *хотя бы один* подагент; ненулевой код будет только при полностью неуспешном запуске. Проверяйте массив `warnings` в JSON-режиме или stderr в текстовом, чтобы увидеть сбойные файлы.

### CI значительно медленнее локального запуска

Две обычные причины:

- **Ограничения скорости модели** — при throttling клиент LLM ждёт и повторяет запросы. Снизьте `--concurrency` (например, до `4`), чтобы не упираться в лимит.
- **Холодный кеш** — если провайдер поддерживает кеширование prompt, первый запуск после развёртывания его не использует. Последующие запуски в том же окне быстрее.

## Вывод и интеграция

### `--audience agent` всё ещё выводит строки прогресса

Убедитесь, что вы не видите **stderr**. Сообщения прогресса иногда попадают туда (предупреждения, ошибки). Чистый stdout, гарантируемый `--audience agent`, удобен для парсеров; чтобы подавить всё, перенаправьте: `ocr review --audience agent 2>/dev/null`.

### JSON-вывод: `{ "files_reviewed": 0, "comments": [] }`

В рабочем дереве не было подходящих файлов. Это намеренно: явная форма позволяет вызывающему коду отличить «нечего проверять» от «в проверенных файлах ничего не найдено». Обычное ревью без комментариев возвращает пустой массив `[]`.

### Где хранятся JSONL сессий?

```
~/.opencodereview/sessions/<path-encoded-repo-path>/<session-id>.jsonl
```

Путь репозитория кодируется заменой `/` и `\` на `-`, а `:` на `_` (например, `/Users/foo/my-repo` → `Users-foo-my-repo`). Просматривайте сессии через `ocr viewer`. Удалите каталог, чтобы очистить историю; OCR создаст кодированный путь при следующем запуске.

## Производительность и стоимость

### Как узнать стоимость токенов?

Включите телеметрию:

```bash
ocr config set telemetry.enabled true
ocr config set telemetry.exporter console
ocr review
```

Вызовы LLM не имеют собственных спанов: они записываются метриками. Следите за `ocr.llm.tokens_used` (счётчик с метками `model` и `type`), `ocr.llm.requests_total` (счётчик с `model` и `status`) и `ocr.llm.request_duration_seconds` (гистограмма с `model`). Экспортёр console выводит агрегаты в строке; для панелей переключитесь на OTLP и отправляйте метрики в свой стек. См. [Телеметрию](../telemetry/).

### Почему ревью так дорого?

- Фаза планирования включается для файлов от 50 строк и добавляет один вызов LLM на файл. Снижение порога уменьшает стоимость, повышение ускоряет небольшие PR.
- `MAX_TOOL_REQUEST_TIMES = 30` — щедрый лимит. Модель, использующая все раунды, расходует больше токенов, чем завершающаяся за 3. Более сильные модели обычно завершаются быстрее. Если вы увеличили `--max-tools` для борьбы с лимитом запросов, стоимость на файл будет расти примерно линейно.
- Сжатие памяти само является вызовом LLM. Длинные подзадачи оплачивают раунды сжатия сверх раундов ревью.

### Как уменьшить число вызовов LLM?

- Добавьте `include`, чтобы OCR не проверял ненужные файлы.
- Уменьшите `--concurrency`, если у аккаунта burst-тарификация.
- Передайте `--background`: более полный начальный контекст иногда позволяет модели обойтись без обращений `file_read` / `code_search`.

## Приватность и безопасность

### OCR отправляет мой код куда-либо?

OCR отправляет ваши **диффы** (и необязательные фрагменты из инструментов чтения) на настроенный endpoint LLM. Больше ничего не покидает компьютер: JSONL сессий и файлы правил остаются локальными.

Если телеметрия включена, флаг `content_logging` проходит через конфигурацию, но сейчас не управляет **никаким** путём кода; содержимое prompt и ответов не экспортируется коллектору независимо от флага. Считайте его зарезервированным и оставляйте `false` в production. Подробнее: [Телеметрия](../telemetry/#логирование-содержимого).

### Можно скрыть секреты до отправки в LLM?

Встроенной функции нет. Рекомендуемый процесс:

1. Не коммитьте секреты в репозиторий.
2. Добавляйте в `exclude` файлы, заведомо содержащие хеш-материалы.
3. Используйте фильтры `git diff --no-textconv` или редактирование перед коммитом, чтобы секреты не попадали в диффы.

Функция «правил маскирования» есть в roadmap; следите за [трекером задач](https://github.com/alibaba/open-code-review/issues).

## Прочее

### Где changelog?

[GitHub Releases](https://github.com/alibaba/open-code-review/releases) — каждый релиз содержит заметки, сгенерированные из Conventional Commits.

### Поддерживает ли OCR VCS помимо Git?

Нет. Провайдеры диффов вызывают `git`. Для SVN / Mercurial / других систем понадобятся новые провайдеры; задача поддержки Hg открыта [здесь](https://github.com/alibaba/open-code-review/issues).

### Почему бинарник называется `opencodereview`, а CLI — `ocr`?

Статический бинарник в релизах назван по проекту (`opencodereview`), а NPM-обёртка устанавливает его как `ocr` для удобства. При сборке из исходников получится `dist/opencodereview`; скопируйте его как `ocr` в `$PATH`.

### Как удалить OCR?

```bash
npm uninstall -g @alibaba-group/open-code-review        # установка NPM
sudo rm /usr/local/bin/ocr                              # установка бинарника
rm -rf ~/.opencodereview                                # всё состояние
```

OCR не записывает данные вне `~/.opencodereview` (кроме загрузки бинарника через NPM), поэтому удаление этого каталога очищает историю, конфигурацию и пользовательские правила.
