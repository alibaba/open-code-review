OCR поставляется с **шестью встроенными инструментами**, которые LLM может
вызывать во время ревью. На этой странице описаны назначение каждого
инструмента, схема входа и примеры ввода/вывода. Полные машиночитаемые
определения лежат в
[`internal/config/toolsconfig/tools.json`](https://github.com/alibaba/open-code-review/blob/main/internal/config/toolsconfig/tools.json).

## Доступность инструментов по фазам

Каждый инструмент объявляет, доступен ли он на фазе **плана**, в
**основной задаче** или в обеих:

| Инструмент | План | Основная | Назначение |
|---|---|---|---|
| `task_done` | ✗ | ✓ | Сигнал «я закончил» — завершает цикл. |
| `code_comment` | ✗ | ✓ | Выпустить комментарий ревью с диапазоном строк и предложением. |
| `file_read` | ✗ | ✓ | Прочитать фрагмент файла из снимка после изменений. |
| `file_read_diff` | ✓ | ✓ | Прочитать diff другого файла, чтобы подтвердить межфайловую проблему. |
| `file_find` | ✓ | ✓ | Найти файлы по ключевому слову в имени. |
| `code_search` | ✓ | ✓ | Grep по репозиторию (литерал или regex). |

`task_done` и `code_comment` намеренно **не** доступны на фазе плана:
планирование — только чтение.

> **Контекстные инструменты — это контекст только для чтения, а не цели
> комментариев.** Промпт `main_task` явно запрещает комментировать
> находки в *других* файлах. `file_read`, `file_read_diff`, `file_find` и
> `code_search` нужны модели, чтобы лучше понять diff текущего файла —
> любая проблема, замеченная при сборе этого контекста, по задумке
> игнорируется. Межфайловые замечания появляются как комментарии только
> когда они видны из **diff текущего файла**.

Чтобы переопределить реестр инструментов, передайте `--tools <path>` к
JSON-файлу той же формы, что и встроенный. Так можно отключить
инструмент, изменить описание или добавить новый инструмент на базе
существующего провайдера.

## `task_done`

Завершить основной цикл.

```json
{
  "name": "task_done",
  "input": { "state": "DONE" }
}
```

| Поле | Обязательно | Смысл |
|---|---|---|
| `state` | да | `DONE` (по умолчанию) или `FAILED`. `FAILED` — для случая «доступными инструментами это буквально невозможно сделать»; почти никогда не верный выбор. |

Когда агент видит `task_done`, он перестаёт вызывать LLM и начинает
обрабатывать накопленные вызовы `code_comment`. `task_done` возвращается
сразу (до записи результата в журнал сессии), поэтому значение `state`
принимается, но **не** сохраняется — и на коды выхода тоже не влияет.

## `code_comment`

Выпустить один или несколько комментариев ревью. Каждый комментарий
привязан к фрагменту кода (`existing_code`), чтобы OCR мог автоматически
вычислить номера строк.

### Схема

```json
{
  "name": "code_comment",
  "input": {
    "path": "string — необязательно, переопределить путь файла для этого комментария",
    "comments": [
      {
        "content": "string — комментарий на настроенном языке",
        "existing_code": "string — фрагмент из diff для привязки",
        "suggestion_code": "string — необязательный фрагмент исправления",
        "thinking": "string — необязательно, рассуждение модели по этому комментарию"
      }
    ]
  }
}
```

`comments` — массив, поэтому модель может выпустить несколько
комментариев одним вызовом инструмента. `content` и `existing_code`
обязательны; `suggestion_code` необязателен, но желателен. `path` —
необязательное переопределение на верхнем уровне: если опущено, агент
подставляет файл, который сейчас на ревью. Агент также автоматически
подставляет `path`, когда модель его не указала, так что модели редко
нужно задавать его явно. `thinking` (на комментарий) сохраняет
рассуждение модели: оно сохраняется в комментарии, но не показывается в
итоговом выводе ревью.

> **`thinking` — поле только времени выполнения.** OCR разбирает и
> сохраняет его, но оно намеренно **не** перечислено в схеме
> `code_comment`, которую модель видит в `tools.json` (там только
> `content`, `existing_code` и `suggestion_code`). Более сильные модели,
> которые всё же отправят блок `thinking`, получат его сохранённым;
> большинство его не шлёт — это нормально.

### Алгоритм привязки

OCR проходит по diff в поисках текста из `existing_code` с помощью
**динамического скользящего окна**. Сопоставление пробуется по порядку:

1. **Новая сторона hunk** — последовательность подряд идущих строк
   **контекста + добавленных** (не только удалённых и не только
   неизменённых), дающая номера строк нового файла. Если не удалось,
   OCR повторяет попытку на **старой стороне hunk** — контекст +
   удалённые строки — с номерами старого файла.
2. **Полный обход нового файла** — если ни один hunk не подошёл, OCR
   построчно сканирует всё содержимое файла после изменений в поисках
   подряд идущих совпадений (`resolveFromFileContent`).
3. **Задача перепривязки** — если текстовое сопоставление всё ещё
   не удалось на нетривиальном diff, OCR запускает промпт
   `RE_LOCATION_TASK`, прося модель заново привязать фрагмент.

Сопоставление **нечувствительно к пробелам**: строки обрезаются по
краям, маркеры diff `+`/`-` снимаются перед сравнением, так что
отступы не обязаны совпадать точно. В крайнем случае комментарий
доставляется с `start_line=0`, сообщая пользователю: «проблема реальна,
но место придётся найти самостоятельно».

### Пример

```json
{
  "comments": [
    {
      "content": "`tx.Rollback()` никогда не откладывается через defer — ранние return утекают транзакцию.",
      "existing_code": "tx, err := db.Begin()\nif err != nil {\n    return err\n}",
      "suggestion_code": "tx, err := db.Begin()\nif err != nil {\n    return err\n}\ndefer tx.Rollback()"
    }
  ]
}
```

## `file_read`

Прочитать диапазон строк файла в его виде **после изменений**.

### Схема

```json
{
  "name": "file_read",
  "input": {
    "file_path": "src/foo.go",
    "start_line": 10,
    "end_line": 80
  }
}
```

| Поле | Обязательно | По умолчанию | Примечания |
|---|---|---|---|
| `file_path` | да | — | Путь относительно корня репозитория. |
| `start_line` | нет | `1` | Нумерация с 1. |
| `end_line` | нет | конец файла | Включительно. |

### Вывод

```
File: src/foo.go (Total lines: 220)
IS_TRUNCATED: false
LINE_RANGE: 10-80
10|package foo
11|
12|import (
13|    "fmt"
…
```

Каждая строка содержимого начинается с 1-индексированного номера строки и
разделителя `|`, чтобы модель могла точно цитировать номера строк в
последующих вызовах `code_comment`.

### Ограничения

- **Не больше 500 строк за вызов.** Более широкие диапазоны обрезаются,
  выставляется `IS_TRUNCATED: true`, и в конец добавляется
  `Note: Results truncated to 500 lines. Please narrow your line range.`
- Читается только **изменённая версия** файла. Чтобы увидеть старую
  версию, используйте `file_read_diff`.

Когда модели нужен окружающий контекст (для комментария о функции,
которую она видит только в diff), диапазон следует вычислять из
заголовка hunk `@@ -x,y +m,n @@` — обычно `m-50` до `m+n+50`.

## `file_read_diff`

Прочитать diff одного или нескольких *других* файлов того же набора
изменений — полезно, когда комментарий зависит от того, был ли обновлён
связанный файл.

### Схема

```json
{
  "name": "file_read_diff",
  "input": {
    "path_array": ["src/api/handler.go", "src/db/queries.go"]
  }
}
```

### Вывод

```
==== FILE: src/api/handler.go ====
--- a/src/api/handler.go
+++ b/src/api/handler.go
@@ -10,1 +10,2 @@
- old line
+ new line 1
+ new line 2

==== FILE: src/db/queries.go ====
@@ -5,1 +5,1 @@
- query := "SELECT *"
+ query := "SELECT id"
```

Если путь не входит в набор изменений, эта запись молча пропускается.
Если **ни один** из запрошенных путей не в наборе изменений, инструмент
возвращает `Error: diff not found for the requested paths`; пустой
`path_array` возвращает `Error: no files found`.

## `file_find`

Найти файлы в репозитории по ключевому слову в имени (подстрока).

### Схема

```json
{
  "name": "file_find",
  "input": {
    "query_name": "UserService",
    "case_sensitive": false
  }
}
```

| Поле | Обязательно | По умолчанию | Примечания |
|---|---|---|---|
| `query_name` | да | — | Подстрока сопоставляется с **basename** каждого файла (часть после последнего `/`), а не с полным путём. |
| `case_sensitive` | нет | `false` | Установите `true` для точного учёта регистра. |

Набор кандидатов берётся из `git ls-files --cached --others
--exclude-standard` в режиме рабочей копии или из `git ls-tree -r
--name-only <ref>` в режиме диапазона / коммита. Файлы без расширения
пропускаются, кроме `Makefile`, `Dockerfile`, `LICENSE`, `Vagrantfile`,
`Containerfile`.

### Вывод

Список путей, разделённых переводами строк:

```
src/main/java/com/example/UserService.java
src/test/java/com/example/UserServiceTest.java
src/main/java/com/example/internal/UserServiceImpl.java
```

Если ни один файл не совпал (или `query_name` пуст), инструмент
возвращает литерал `// The file was not found`.

### Ограничения

Возвращает до **100** совпадений; остальное молча обрезается. Если
модели нужен более широкий поиск, она должна перейти к `code_search`.

## `code_search`

Полнотекстовый поиск по репозиторию. Основан на `git grep`, поэтому
понимает синтаксис `pathspec` и учитывает `.gitignore`.

### Схема

```json
{
  "name": "code_search",
  "input": {
    "search_text": "TODO|FIXME",
    "file_patterns": ["*.go", ":(exclude)vendor/"],
    "case_sensitive": false,
    "use_perl_regexp": true
  }
}
```

| Поле | Обязательно | По умолчанию | Примечания |
|---|---|---|---|
| `search_text` | да | — | Литерал или PCRE-шаблон (см. `use_perl_regexp`). |
| `file_patterns` | нет | весь репозиторий | Массив записей pathspec. Используйте `:(exclude)pat` для исключения. |
| `case_sensitive` | нет | `false` | — |
| `use_perl_regexp` | нет | `false` | При `true` `search_text` трактуется как regex. |

### Вывод

Результаты группируются по файлам. Каждая группа начинается с
`File: <path>` и `Match lines: <n>`, затем по одной строке
`line|content` на совпадение:

```
File: path/to/example.java
Match lines: 2
433|      String name = toolRequest.get().getName();
438|      logToolRequest(newPath, tool, toolRequest.get());

File: path/to/other.java
Match lines: 1
22|      var req = new ToolRequest();
```

Если совпадений нет, инструмент возвращает литерал `No matches found`.

### Шпаргалка pathspec

| Цель | `file_patterns` |
|---|---|
| Один файл | `["src/main.go"]` |
| Все Go-файлы | `["*.go"]` |
| Все Go, кроме тестов | `["*.go", ":(exclude)*_test.go"]` |
| Только один каталог | `["src/api/"]` |
| Несколько типов, без vendor | `["*.go", "*.ts", ":(exclude)vendor/", ":(exclude)node_modules/"]` |

### Ограничения

- Ограничивает совпадения до **100 на файл** через
  `git grep --max-count 100`, поэтому суммарный вывод по многим файлам
  может превысить 100. Когда срабатывает лимит на файл, вывод
  предваряется `Note: The results have been truncated. Only showing
  first 100 results.`.
- Пустой / состоящий только из пробелов `search_text` возвращает
  `Error: search_text is blank` вместо развёртывания на каждую строку.
- В режиме рабочей копии ищет по **текущему рабочему дереву**, в режиме
  диапазона / коммита — по разрешённому целевому ref (`FileReader.Ref`
  передаётся как позиционный аргумент в `git grep`).

## Выполнение инструментов и ошибки

Инструменты выполняются синхронно внутри цикла агента, с двумя
исключениями:

- `code_comment` отправляется в **CommentWorkerPool**, чтобы цикл не
  блокировался на разрешении строк и reflection.
- `task_done` завершается коротко — возвращается сразу, не вызывая
  никакого провайдера.

Когда инструмент ошибается (сеть, неверные аргументы, файл не найден),
результат доставляется модели как обычный tool result с текстом вроде
`"Error: file not found: src/missing.go"`. Затем модель решает,
повторить попытку, запросить другой файл или вызвать `task_done`.

Если имени инструмента нет в реестре, OCR возвращает константу
`tool.NotAvailableMsg`, а не падает. Поэтому отключение инструментов
во время выполнения (через `--tools`) безопасно.

## Настройка инструментов

Два пути расширения:

### 1. Отключить инструмент

Скопируйте `tools.json`, удалите ненужную запись и запустите:

```bash
ocr review --tools ./my-tools.json
```

Например, если нужен ревьюер «только комментарии», который никогда не
читает дополнительный контекст, оставьте только `code_comment` и
`task_done`.

### 2. Переописать инструмент

Сохраните `name` (провайдеры внутри ищутся по имени), но измените
`description`, чтобы подтолкнуть модель. Это самый простой способ
внедрить проектные подсказки — например: «При использовании `file_read`
всегда читайте не меньше 30 строк вокруг изменения».

> Добавление **новых** *имён* инструментов требует проводки на стороне
> Go; см. `internal/tool/definitions.go` и провайдеры в
> `internal/tool/`. Один JSON-файл не добавит новое поведение.
