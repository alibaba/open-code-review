ACP 対応クライアントの会話から OCR のレビューとスキャンを実行できます。`ocr-acp`
アダプターは Agent Client Protocol（ACP）を使ってエディターとローカルの
OCR CLI を接続し、進捗、指摘、ファイルの位置を会話に表示します。
修正案を報告しますが、ファイルを編集することはありません。

ACP はエディターと agent を接続するオープンなプロトコルです。クライアントはアダプターを
独立したローカルプロセスとして起動し、stdio で JSON-RPC メッセージを交換します。
アダプターはリクエストを検証して `ocr review` または `ocr scan` を実行し、
OCR の構造化出力をクライアントへの更新に変換します。
OCR のレビューエンジンとモデル設定は、アダプターから独立しています。

## 前提条件 {#prerequisites}

- [OCR CLI](../../installation/) をインストールし、[レビューモデル](../../configuration/)
  を設定してください。`ocr llm test` で接続を確認できます。
- アダプターのビルドには、`acp/` ディレクトリを含むソースのチェックアウト、Git、
  Go 1.23 以降が必要です。親プロジェクトの OCR CLI のビルドには Go 1.25.5 以降が必要です。
- ACP v1 の stdio とカスタム agent 起動コマンドに対応したクライアントを使用してください。macOS arm64 ではローカルの
  自動テストを実施しています。Linux の `aa7d4e7` は [ACP CI](https://github.com/alibaba/open-code-review/actions/runs/34986645165) に合格し、
  プロセス終了処理、race 検出、公式 Python ACP SDK の smoke テストを含みます。Windows は現在サポートしていません。

アダプターは OCR CLI とは別にビルドします。以下の手順ではローカルでビルドした
ものを使用します。OCR の npm パッケージに ACP バイナリが同梱されていることを
前提としていません。

## ビルドとクライアントへの接続 {#build-and-connect-your-client}

リポジトリのルートで実行します。

```bash
make -C acp build
command -v ocr
```

ビルドすると `dist/ocr-acp` が作成されます。`ocr` の検索結果として表示された
絶対パスを、以下の `--ocr-binary` の値に指定してください。

クライアントに `OpenCodeReview` というカスタム ACP agent を登録し、
ACP v1 stdio を選択して、次の起動コマンドを設定してください。

```bash
/absolute/path/open-code-review/dist/ocr-acp --ocr-binary /absolute/path/ocr
```

両方の実行ファイルに絶対パスを指定し、プロジェクトの作業ディレクトリを選択します。
設定フィールド名はクライアントごとに異なるため、その ACP 設定手順を参照してください。
新しい OpenCodeReview 会話では、解析用モデルなしでスラッシュコマンドを使えます。
OCR 自体のレビューモデルは引き続き必要です。

## レビューとスキャンの実行 {#run-a-review-or-scan}

OpenCodeReview の会話で、以下のコマンドを送信します。

| リクエスト | コマンド |
| --- | --- |
| ステージ済み、未ステージ、未追跡の変更をレビュー | `/review` |
| レビューを最大 1 ラウンド実行 | `/review --effort low` |
| 現在チェックアウトしている最新コミットをレビュー | `/review --commit HEAD` |
| 既存の 2 つの参照を比較 | `/review --from main --to HEAD` |
| ディレクトリをスキャン | `/scan --path internal/agent` |
| 複数のパスをスキャン | `/scan --path internal/agent,internal/config` |

例の参照とパスは、プロジェクト内のものに置き換えてください。レビューには Git
リポジトリが必要で、指摘のパスはそのルートを基準に解決します。スキャンではセッションの
作業ディレクトリを使用します。`--effort low` は最大 1 ラウンド、`medium` は最大 2 ラウンド、
`high` は最大 3 ラウンドのレビューを実行します。新しい指摘がなければ、早期に終了する場合があります。
省略すると OCR の設定を維持します。
ラウンドを減らすと問題を見逃す可能性があるため、速度と品質のバランスを考慮してください。

ACP のコマンド候補に対応したクライアントでは、`/` を入力するとコマンドと引数の
ヒントを確認できます。ブランチやパスの動的補完は提供しません。クライアントが
ローカルファイルへのリンクを添付する場合は、`/scan` と一緒に送り、`--path` を
省略してください。リンクと `/review` または明示的なスキャンパスは併用できません。
未対応または曖昧なリンクは拒否し、スキャン範囲を自動で広げることはありません。

アダプターが受け付ける CLI オプションは以下に限定されており、任意のオプションを
そのまま渡すことはできません。

- レビュー：`--commit`、`--from`、`--to`、`--effort`、`--no-filter`、
  `--background`、`--background-file`。
- スキャン：`--path`、`--batch`、`--no-plan`、`--no-dedup`、`--no-summary`、
  `--background`。

変更全体をレビューするには `/review` を使用してください。`--staged` は未対応です。
会話内のコマンドでは、`--format` や `--audience` などの出力オプション、
`--repo`、`--model`、`--provider` などの上書きオプションは受け付けません。
レビューモデルは OCR 側で設定してください。

## 自然言語のリクエストを有効にする {#enable-natural-language-requests}

解析用モデルは、自然言語のリクエストをレビューやスキャンのコマンドに変換するか、
不明点を確認します。OCR のレビューモデルとは別に設定します。
クライアント自体のモデルを選択しても、この 2 つのモデルは設定されません。

agent の `env` オブジェクトに以下の環境設定を追加し、モデルとキーのプレースホルダーを
プロバイダーの値に置き換えてください。

```json
{
  "OCR_ACP_PARSER_PROVIDER": "openai",
  "OCR_ACP_PARSER_MODEL": "YOUR_TOOL_CALLING_MODEL",
  "OCR_ACP_PARSER_API_KEY": "YOUR_PARSER_API_KEY"
}
```

この例では OpenAI 互換の Chat Completions プロトコルを使用します。Anthropic Messages
プロトコルには `anthropic` を指定します。互換ゲートウェイを使用する場合は、
`OCR_ACP_PARSER_BASE_URL` に API のベース URL も設定してください。認証情報は
ローカル設定に保存するか、agent プロセスの環境変数で渡してください。共有する
プロジェクト設定に含めてコミットしないでください。GUI アプリは、ターミナルで
エクスポートした環境変数を引き継がない場合があります。

ベース URL のパス規則はプロトコルによって異なります。

| プロトコル | `OCR_ACP_PARSER_BASE_URL` の例 | リクエスト先 |
| --- | --- | --- |
| `openai` | `https://gateway.example/v1` | `https://gateway.example/v1/chat/completions` |
| `anthropic` | `https://gateway.example` | `https://gateway.example/v1/messages` |

それぞれ `/chat/completions` または `/v1/messages` で終わる完全なエンドポイントも使用できます。
その場合、同じ接尾辞は追加しません。Anthropic のベース URL が `/v1` で終わると
`/v1/v1/messages` になるため、ゲートウェイの実際の API パスに合わせて指定してください。

| 環境変数 | 起動フラグ | 用途 |
| --- | --- | --- |
| `OCR_ACP_PARSER_PROVIDER` | `--parser-provider` | `openai` または `anthropic` |
| `OCR_ACP_PARSER_MODEL` | `--parser-model` | ツール呼び出しに対応したモデル |
| `OCR_ACP_PARSER_BASE_URL` | `--parser-base-url` | API ベース URL の上書き（任意） |
| `OCR_ACP_PARSER_API_KEY` | なし | 解析用 API キー。環境変数のみ |

起動フラグは、対応する環境変数より優先されます。解析用モデルは OCR の設定や
`OCR_LLM_*` 変数を読み取りません。対応するプロトコルは `openai` と `anthropic`
であり、ここでは `openai-responses` と `anthropic-bedrock` は使用できません。

Anthropic の解析リクエストでは、必須の `submit_intent` ツール呼び出しを使用するため、
Thinking を明示的に無効にします。OCR のレビューモデルの Thinking 設定は変更しません。

解析用モデルを設定したら、新しい会話を開始して試してください。

```text
作業ディレクトリの変更をレビューしてください。
現在チェックアウトしている最新コミットをレビューしてください。
internal/agent をスキャンして、潜在的なバグを探してください。
```

リクエストが曖昧な場合は、実行前に確認への回答が必要です。モデルには、質問や案内を
ユーザーと同じ言語で返すよう指示しています。固定の検証メッセージとレポートのラベルは
英語のままです。解析用モデルが利用できなくても、スラッシュコマンドは使えます。
解析用モデルの設定が不完全な場合は、起動時に明示的なエラーが発生します。

「現在チェックアウトしている最新コミット」は `/review --commit HEAD` に対応します。
セッションは確認待ちのリクエストを 1 件だけ保持します。連続した確認では互換性のある複数の既知の
フィールドを保持し、明示された新しい値を優先します。異なるレビュー種別のフィールドは混在させません。
完了またはキャンセルで状態を消去し、別のセッションには復元しません。

## 結果の確認とキャンセル {#read-results-and-cancel-work}

**Command:** ブロックには、実行中のコマンドが表示されます。**OCR progress** には
作業ディレクトリと、長さを制限したプレーンテキストログの末尾が表示されます。
展開すると詳細を確認できます。ログはこの項目内で更新され、会話に重複して追加されません。
最初から展開するか折りたたむかは、クライアントが制御します。

指摘は最終メッセージに一度だけ表示され、重大度、カテゴリ、説明、修正コードの提案が
含まれます。指摘ごとのカードや移動ボタンは追加しません。有効な位置情報を持つ
既存ファイルは、本文のリンクから開くことができます。存在しないファイル、範囲外の行、作業ルート
の外にあるパスは、移動リンクを付けずにテキストを残します。表示とクリック時の動作は
クライアントのバージョンに依存します。

最終結果には、取得できたサマリー、一部失敗の詳細、合計トークン数、OCR が報告した
経過時間が含まれます。トークンの合計はすべてのモデルリクエストを対象とし、新しく生成した
回答のトークン数だけを表すものではありません。

実行中のリクエストは、クライアントのキャンセル操作で停止できます。アダプターは処理を
キャンセルし、管理対象プロセスの終了処理が完了するまで待機します。解析を含むターン全体に
制限時間を設けるには、agent の `args` 配列に `"--turn-timeout", "10m"` を追加します。
デフォルトは `0` で、ターン全体のタイムアウトは無効です。解析には個別にデフォルト
15 秒の制限があります。タイムアウト時は、アダプターが再試行を案内します。

## トラブルシューティング {#troubleshooting}

| 症状 | 確認すること |
| --- | --- |
| agent が起動しない | 2 つの実行ファイルの絶対パスと実行権限を確認してください。`ocr llm test` で OCR の設定を確認し、不完全な解析用モデルの設定は削除するか、必要な値をすべて指定してください。 |
| スラッシュコマンドは動くが、自然言語は使えない | 別途 `OCR_ACP_PARSER_*` 環境変数を設定してください。プロバイダー、モデル、キー、ゲートウェイ URL を確認してください。 |
| 自然言語の解析がタイムアウトする | 解析のデフォルト制限は 15 秒で、この段階では OCR は未起動です。診断のリクエスト段階、HTTP ステータス、プロバイダーの応答から原因を調べてください。`--turn-timeout` を延長しても解析自体の制限は延びません。再試行するか、`/review`、`/scan` で解析用モデルを迂回できます。 |
| コマンドやフラグが拒否される | 上記の対応オプションを使用してください。`/review --path` の代わりに `/scan --path` を使用し、コミットや範囲のレビューには既存の Git 参照を指定してください。 |
| レビューが失敗する、または一部の結果しか返らない | OCR progress を展開して診断情報を確認し、最終結果の失敗詳細を読んでください。OCR のモデル設定とプロバイダーの稼働状況を確認してください。 |
| 結果の位置をクリックできない | ファイルが処理対象のルート内に存在し、行範囲が有効か確認してください。テキストだけを表示するフォールバックは意図した動作です。 |
| 処理に時間がかかりすぎる | キャンセルするか、進捗の詳細を確認するか、ターン全体のタイムアウトを設定してください。レビューでは `--effort low` でラウンド数を減らせます。 |
| 再ビルド後も古い動作のまま | 設定したバイナリのパスを確認し、新しい agent 会話を開始してください。古いプロセスを再利用している場合は、agent またはクライアントを再起動してください。 |

接続に問題がある場合は、クライアントの ACP ログとアダプターの stderr を確認します。
共有する前に、認証情報と非公開のソース情報を削除してください。

## 更新とサポート範囲 {#upgrade-and-support-boundaries}

ソースのチェックアウトを更新し、`make -C acp build` を再実行して、新しい
OpenCodeReview の会話を開始してください。実行中のプロセスや過去のメッセージは
再読み込みされません。セッションの復元には対応していません。新しい会話は、回答待ちの
確認状態を引き継がずに開始します。

アダプターは現在、ローカルの stdio トランスポートを使用します。HTTP トランスポート、
追加のワークスペースルート、ファイルの自動編集、画像や音声のプロンプトには対応していません。
ほかの ACP クライアントは、それぞれ互換性の確認が必要です。プロトコルテストの成功だけで、
すべてのクライアントの画面上の動作が確認できるわけではありません。
