> Favor precision over recall: only raise an issue when you are confident it is a real defect, and stay silent when the surrounding context is unclear — a false alarm costs more reviewer trust than a missed minor issue. Treat security and correctness findings as blocking, and style or idiom suggestions as non-blocking. Review only what is observable in the Dhall under review; do not infer the contents of an imported file, the behavior of the remote endpoint behind a URL import, or the value an `env:` variable will hold at render time.

#### Obvious Typos or Spelling Errors
- Spelling errors in `let` binding names, record field names, and union alternative names at their declaration sites; do not report spelling errors at reference sites
- Typos in comment text that describe a schema's public interface and would mislead a consumer

#### Remote Imports and Integrity Hashes
- A remote import by URL with no trailing `sha256:<hex>` integrity hash — an unpinned dependency whose content can change under the project without any diff; `dhall freeze` adds the hash
- An integrity hash that appears hand-edited, or one left unchanged while the import target visibly moved in the same diff (a new tag, commit, branch, or path) so it can no longer match — the fix is re-running `dhall freeze`, never editing the hex by hand
- An `env:` import supplying a credential, or an `env:` fallback after `?` holding a real-looking secret rather than an obvious placeholder (`env:DB_PASSWORD as Text ? "password"`)
- Do not flag a bare relative import (`./types.dhall`, `../Prelude/package.dhall`) for lacking a hash — local imports are the overwhelming majority and pinning them is not the convention
- Do not flag the `missing sha256:<hex> ? ./local.dhall` idiom used throughout the Prelude; that is a content-addressed cache lookup with a working local fallback, not an unpinned import

#### Totality and Evaluation
- Dhall is total and has no recursion, so a `let` binding that refers to itself is a design error rather than a style nit — the intended construction is `Natural/fold`, `List/fold`, or another explicitly bounded fold
- A fold given a very large `Natural` bound, which is normalized eagerly and makes rendering slow or memory-hungry
- Do not flag ordinary use of `Natural/fold` / `List/fold`; folds are the idiomatic way to express iteration in a total language

#### Optionals, Records, and Unions
- An `Optional` consumed by `merge` or a fold whose `None` branch silently substitutes a value indistinguishable from a real one, hiding a missing setting instead of surfacing it
- Record completion `Type::{ ... }` where the defaults record already supplies a field the surrounding code clearly meant to set, so the default is applied silently — the typechecker cannot catch this, unlike a missing required field or a misspelled field name, which it already rejects
- A new alternative added to a union in the same diff without updating every `merge` over that union — each becomes non-exhaustive and fails to typecheck, so name the `merge` sites that need the new handler

#### Generated Output and Rendering
- A committed artifact rendered by `dhall-to-yaml` / `dhall-to-json` that lacks the `# Code generated by dhall-to-yaml.  DO NOT EDIT.` header (emitted by `--generated-comment`), leaving no signal against hand-editing it
- A hand-edit to a file carrying that generated header — the change belongs in the `.dhall` source, and the artifact must be regenerated
- A secret sourced from `env:` that ends up rendered into a committed YAML/JSON artifact
- Whether rendered output is committed or generated in CI is a project convention; flag inconsistency with sibling artifacts in the same diff, not the choice itself
