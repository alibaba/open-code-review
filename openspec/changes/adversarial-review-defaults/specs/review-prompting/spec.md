# Spec Delta

## Purpose

定义 `ocr review` 的默认评审姿态:评审 agent 必须主动猎取哪些失效类别、每条发现必须满足的实质性门槛、以及保证多轮评审不灌水的校准规则——并入默认 prompt,使每次评审默认携带对抗性实质内容,无任何 opt-in。

## ADDED Requirements

### Requirement: 评审 agent 应主动猎取列明的失效类别

默认 `ocr review` prompt 应(SHALL)指示评审 agent 主动探查一组明列的高代价失效类别,而非仅描述 diff 做了什么。被猎取类别应包括:授权、权限、租户隔离与信任边界;数据丢失、损坏、重复与不可逆状态变更;回滚安全、重试、部分失败与幂等缺口;竞态条件、顺序假设、过期状态与重入;空态、null、超时与依赖降级行为;版本漂移、schema 漂移、迁移隐患与兼容性回归;以及掩盖失效或阻碍恢复的可观测性缺口。

#### Scenario: diff 引入幂等缺口

- **WHEN** 被评审的 diff 在非幂等操作外包了一层重试循环
- **THEN** 评审对该操作的幂等缺口产出一条发现

#### Scenario: diff 仅触及格式

- **WHEN** 被评审的 diff 只改格式、无任何行为影响
- **THEN** 评审不为它编造失效类别的发现

### Requirement: 每条发现应满足实质性门槛

评审 agent 应(SHALL)只提交实质性发现。每条发现应指明:会出什么事、为什么这条代码路径脆弱、可能的影响、以及能降低风险的具体改动。每条发现应以已评审的 diff 或工具输出为依据;agent 不得引用其未观察到的文件、行号或代码路径。纯风格、命名或低价值清理类反馈不得作为发现提交。

#### Scenario: 有真实影响的缺失守卫

- **WHEN** diff 新增的代码路径在超时分支解引用可能为 nil 的值
- **THEN** 提交的评论说明失效模式、脆弱路径、影响与具体修复

#### Scenario: 仅风格层面的观察

- **WHEN** 评审 agent 注意到一个无行为后果的重命名机会
- **THEN** 不为它提交发现

### Requirement: 校准规则应防止灌水发现

评审 prompt 应(SHALL)指示评审 agent 宁要一条强发现也不要多条弱发现;变更安全时就明说(不提交发现),而不是编造问题。在首轮之后的每个评审轮次,agent 不得仅仅因为更早的轮次已确认了真实发现,就编造新发现。

#### Scenario: 后续轮次无新增内容

- **WHEN** 第二评审轮开始,且所有真实发现已在首轮提交
- **THEN** agent 不再提交额外发现,而不是用弱发现凑数

#### Scenario: 安全的变更

- **WHEN** 被评审的 diff 不含实质性问题
- **THEN** 评审以零发现完成,且无编造的问题

### Requirement: 对抗姿态默认生效且不改变范围规则

上述姿态应(SHALL)在没有任何命令行 flag 或配置键的情况下,作用于每一次 `ocr review`。新 prompt 小节不得放松既有的文件范围约束:评论仍应只针对当前评审组内的文件;评论输出结构(severity、category、行定位)保持不变。`ocr scan` 流水线不受该姿态影响。

#### Scenario: 裸调用即携带姿态

- **WHEN** 用户不带任何姿态相关 flag 运行 `ocr review`
- **THEN** 加载的评审 prompt 包含失效类别优先级、实质性门槛与校准小节,且未提供任何 flag

#### Scenario: 范围约束仍然生效

- **WHEN** 评审 agent 对当前评审组之外的文件形成判断
- **THEN** 它不提交针对该文件的评论

#### Scenario: scan 保持不变

- **WHEN** 用户运行 `ocr scan`
- **THEN** scan prompt 仍是独立的 scan 模板,不含并入的姿态小节
